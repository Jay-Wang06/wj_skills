# Explain Diff

把 git diff（或粘贴的 patch）写成清晰、便于评审的说明。除非用户要求，否则不要改代码。

## 工作流

1. **拿到 diff**（范围尽量小）：
   - 未提交：`git diff` 与 `git diff --staged`
   - 分支相对基线：`git diff <base>...HEAD`（优先三点 diff）
   - 单次提交：先 `git show --stat`，需要时再 `git show`
   - 用户粘贴的 patch：直接用；不要臆造文件
2. **先看结构**：文件列表、重命名、生成物/vendor 噪音。锁文件/二进制抖动若与行为无关可忽略。
3. **按意图分组**，不要只按路径（如「鉴权校验」「API 接线」「测试」）。
4. **按下方模板写说明**。
5. **保持事实**：意图不清就说不清，并列出 1～2 种合理解读——不要编造产品需求。

## 输出模板

```markdown
## 摘要
[1～3 句：用人话说明这次改动做什么]

## 分块改动
### [区域 / 意图名]
- **改了什么**：[行为或 API 变化]
- **在哪里**：`path/to/file`（必要时标注关键符号）
- **备注**：[仅非显而易见时]

## 影响
- **用户 / API 侧**：[可见行为、契约、UI——或「无」]
- **内部**：[数据流、依赖、触及的调用点]
- **影响半径**：[低 / 中 / 高] — [一句话原因]

## 风险与注意点
- [回归、边界、迁移、性能、安全——或「暂无明显风险」]

## 建议验证
- [ ] [具体检查：测试、手工路径或命令]
```

## 语气与约束

- 短条目优先，少写长文。先讲行为，不要逐行念 diff。
- 明确标出破坏性变更、schema/迁移需求、安全敏感改动。
- 区分 **重构**（行为不变）与 **行为变更**。
- 纯风格噪音可跳过，除非掩盖了真实改动。
- diff 很大时：先总结热点，再问是否深入某一块。
- 语言：跟用户一致（中文↔中文，英文↔英文）。

## 反模式

- 不要大段贴回代码；引用路径/符号即可。
- 除非用户要求，不要做成完整 code review（不要挑刺清单）。
- 除非用户要求，不要建议 commit/PR。
