# Changelog User

写给 **用户** 看的更新说明，不是给开发看的。先讲结果，隐藏实现细节。

## 工作流

1. **收集输入**（有什么用什么）：
   - commit 主题 / PR 标题 / milestone 列表
   - `git log <prev>..HEAD --oneline` 或粘贴列表
   - 可选：标题含糊时再扫关键 diff
2. **归类**每条：新增 / 改进 / 修复 / 移除 / 破坏性 / 内部
3. **丢掉或降级**纯内部项（重构、CI、依赖），除非改变用户可见行为或安全。
4. **用结果导向语言**按模板改写。
5. **检查**：无黑话泄漏、无文件路径、工单号不能单独当标题（需配人话）。

## 输出模板

```markdown
## [版本或日期] 更新了什么

### 新增
- …

### 改进
- …

### 修复
- …

### 移除
- …

### 破坏性变更
- **[什么坏了]** — [用户该怎么做]
```

空分区省略。若只有修复：短引言 + 修复列表即可。

**可选一句话**（应用商店 / 横幅）：

```markdown
> [一句话亮点]
```

## 文风规则

| 要这样写 | 不要这样写 |
|----------|------------|
| 「支持将报表导出为 CSV」 | 「新增 CsvExporter 并接线 blob 接口」 |
| 「登录可保持 30 天」 | 「把 JWT TTL 调到 2592000」 |
| 「大项目下图表加载更快」 | 「给 Redux selector 做 memoize」 |
| 「修复打开空文件夹时崩溃」 | 「在 FolderView#mount 加空值检查」 |

- 第二人称或中性产品口吻：「你可以…」/「现已支持…」
- 具体优于空泛：点名界面（设置、导出、移动端）。
- 合并重复；相关的小修复可诚实收成一条。
- 破坏性变更：必须给出用户迁移/应对动作。
- 安全修复：如实说明但不要写利用细节（「修复可能导致…泄露的问题」）。
- 语言跟用户一致。

## 篇幅建议

| 受众 | 目标 |
|------|------|
| 应用内 What's New | 3～8 条 |
| GitHub Release | 分组呈现，仍以用户为先 |
| 邮件 / 博客 | 短引言 + 条目；不要堆 commit |

## 反模式

- 不要把原始 conventional-commit 列表当最终文案。
- 不要编造源列表里没有的功能。
- 没有用户侧证据时，不要把内部改动写成「性能优化」。
- 除非用户要，不要带 PR 号（要的话放后面，不要当标题）。
