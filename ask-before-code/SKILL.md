# Ask Before Code

先问清楚再动手，避免做错方向。只问少量尖锐问题，确认后再实现。

## 何时启用

满足 **任一** 条件时使用本 skill：

- 目标含糊（「弄好一点」「像 Y 那样加个 X」）
- 存在多种合理设计
- 触及 API 契约、数据模型、鉴权或迁移
- 未说明成功标准
- 未划定范围边界（做 / 不做）

**可跳过**（直接开写）当：

- 改动很小且局部显而易见（错字、单文件重命名、明确的一行修复）
- 用户已给出验收标准与约束，并说「直接做」
- 明确只要探索 / spike，不承诺交付

## 工作流

```
动手前先问：
- [ ] 1. 用一句话重述目标
- [ ] 2. 只问阻塞问题（最多 3～5 个）
- [ ] 3. 确认范围内 / 范围外
- [ ] 4. 给出薄计划
- [ ] 5. 等待确认（用户已说继续则可跳过）
- [ ] 6. 实现
```

### 1. 重述目标

一句话：对用户而言什么叫成功。说不清楚，本身就是第一个问题。

### 2. 只问阻塞问题

最多 **3～5** 个。能给选项就别让用户写作文。每个问题必须能解锁设计或验收。

缺口覆盖这些方面：

| 方面 | 未知时要问 |
|------|------------|
| **结果** | 做完后用户能做什么？ |
| **验收** | 如何判定可用？（例子 / 测试 / 演示路径） |
| **约束** | 性能、兼容、安全、离线、截止日期？ |
| **形态** | CLI / API / UI / 库——哪一种、给谁用？ |
| **数据** | 新字段、迁移、是否要向后兼容？ |
| **非目标** | 明确不要做什么？ |

仓库或上文已能推断的，**不要再问**。

### 3. 范围围栏

简要写明：

- **范围内**：…
- **范围外**：…
- **待定**：…（仅仍阻塞时）

### 4. 薄计划

最多 3～7 步。已知则点名文件/模块。标出风险（破坏性变更、迁移）。非必要不做新架构。

### 5. 确认开工

除非用户已授权实现，问完 + 计划后先停。若只答了一部分：已定部分可继续，未定部分保持可见。

## 输出模板

```markdown
## 目标
[一句话]

## 问题
1. …？
2. …？（选项：A / B / C）
3. …？

## 范围
- **内**：…
- **外**：…

## 计划（待回答后）
1. …
2. …
```

## 约束

- 语言跟用户一致。
- 选项清晰时优先选择题。
- 不要「顺便」大重构。
- 不要把问题埋在长文里——先给「目标 + 问题」。
- 用户说「你定」时：选合理默认、说清楚，再实现。
