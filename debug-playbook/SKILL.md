# Debug Playbook

用证据排错。优先最小修复，避免大范围重写。在复现清楚或边界明确之前，不要急着改代码。

## 工作流

复制并跟踪进度：

```
排错进度：
- [ ] 1. 记录现象
- [ ] 2. 复现 / 界定范围
- [ ] 3. 假设（排序）
- [ ] 4. 用证据验证
- [ ] 5. 最小修复
- [ ] 6. 回归检查
```

### 1. 记录现象

只收集必要信息：

- 期望 vs 实际行为
- 报错信息 / stacktrace / 退出码
- 何时开始（提交、发布、依赖变更）——若已知
- 环境线索（OS、运行时版本、环境变量）——缺失且阻塞时再问

### 2. 复现 / 界定范围

- 优先 **最小可靠复现**（命令、请求、UI 路径或测试）。
- 无法复现：按输入、分支、配置、近期 diff 收窄，并说明已尝试步骤。
- 用户无法复现：界定边界（必现 / 偶发 / 仅在 X）。

### 3. 假设（排序）

列 2～4 条假设，最可能的在前。每条必须 **可证伪**。

差：「鉴权有问题。」
好：「JWT 过期时间按秒解析，但签发方给的是毫秒。」

### 4. 用证据验证

针对最可能的假设：

- 阅读相关代码路径（不要臆造 API）。
- 像回归时再查近期 diff：`git log` / `git blame` / 确有必要时才 `git bisect`。
- 增加或运行聚焦检查（日志、断言、失败测试、一次 curl/查询）——禁止投机式重构。

每条假设标记：**已确认** / **已排除** / **尚无定论** + 一行证据。

### 5. 最小修复

- 只改能根治问题的最小面。
- 同一次改动里不做顺手清理。
- 多种修法并存时，选最好验证、最好回滚的。
- 根因在别处（脏数据、配错、上游）：先说明，再考虑打补丁绕过。

### 6. 回归检查

- 重跑复现步骤，确认符合期望。
- 建议 1～3 个邻近仍应通过的场景。
- 若补测试，紧扣该 bug。

## 输出模板

报告时用此结构（按严重程度调整篇幅）：

```markdown
## 现象
- **期望**：…
- **实际**：…
- **复现**：…

## 假设
1. … — [已确认|已排除|尚无定论]：…
2. …

## 根因
[一小段说明，或「仍未知——下一步探测是…」]

## 修复
[改了什么、为何算最小——只读模式下则给建议方案]

## 验证
- [ ] 复现已通过
- [ ] [邻近场景]
```

## 场景捷径

| 信号 | 优先动作 |
|------|----------|
| 清晰 stacktrace + 本地可复现 | 从栈顶帧建立假设 |
| 「我这边是好的」 | 对比环境、版本、配置、密钥、工作目录 |
| 偶发 | 竞态、时间、重试、资源上限——找可靠触发条件 |
| 仅 CI | 对比镜像、环境变量、并行度、时序 |
| 依赖升级后 | changelog + lockfile + 破坏性 API 调用点 |

## 约束

- 语言跟用户一致。
- 不要长问卷；最多 1～3 个阻塞问题。
- 没有证据不要宣称根因。
- 不要把排错变成无关重写或完整 code review。
- 优先引用路径/符号，避免大段贴代码。
