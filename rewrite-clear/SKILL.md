# Rewrite Clear

把含糊文字改成别人能照着做的表述。保留原意；不要编造需求。

## 工作流

1. **识别来源**：需求、邮件/消息、会议纪要、缺陷报告，或混合。
2. **抽取意图**：谁要什么、何时要、怎样算完成——若文中有。
3. **标出缺口**：列出未知项，不要用猜测填满。
4. **按匹配模板改写**。
5. **默认给一版紧凑稿**；原文很长时再加更短的「一句话摘要」。

## 输出模板

### 需求 / 功能诉求

```markdown
## 清晰版
**角色**：[谁]
**需要**：[能做什么]
**完成标准**：[可观察的验收]
**约束**：[限制——或「未说明」]

## 待确认
- [仅真正阻塞的问题]
```

### 邮件 / 聊天消息

```markdown
## 清晰版
[主题或首行，如有用]

[正文：目的 → 请求 → 背景 → 截止/下一步]
```

礼貌程度贴合原文；删掉套话（「再跟进一下」「对齐一下 synergy」之类）。

### 会议纪要 / 头脑风暴

```markdown
## 决议
- …

## 待办
- [负责人] — [任务] — [若有截止日期]

## 停车场
- [未承诺的想法]
```

### 缺陷 / 事故报告

```markdown
## 清晰版
- **期望**：…
- **实际**：…
- **复现**：…
- **影响**：…
```

## 改写规则

- 多用具体动词和名词，少用形容词（「慢」「更好」「尽快」）。
- 指代不清时，把「它/这个/他们」换成具名主语。
- 一句一事；复合请求拆开。
- 保留原文中的数字、名称、路径和引语。
- 推断内容标 **（推断）**——宁可提问，不要默默编造。
- 语言跟用户一致（中文↔中文，英文↔英文）。

## 反模式

- 除非要求，不要扩成完整 PRD。
- 不要为了「听起来更专业」而改含义。
- 不要虚构截止日期、负责人或验收标准。
- 不要训写作课——直接交付改写结果。
